# FileRelay 实施计划

版本：v1.3 产品规则确认版　日期：2026年11月5日

FileRelay 面向个人及少量熟人使用，重点是两台设备之间的临时文件传递。A 设备设定一个不超过 4 位的数字口令，B 设备输入相同口令，即可互相看到文件并下载；浏览器记住配对关系，后续打开直接使用。

同一口令定位同一组，第三台及后续设备需要任意一台已加入设备确认后才能访问文件，不能仅凭口令直接加入。前两台设备沿用直接配对流程，已记住且凭证有效的设备重开页面不重复申请。口令在当前配对关系中保持固定，忘记后可以重新输入另一个口令，让需要互传的设备使用同一个新口令。前台不提供空间创建、停用、重置口令、空间列表或切换空间功能。

长期文件如何保留暂不设计，首版以临时中转为目标，新文件最多保留 24 小时。不将永久保存及保存方式切换作为首版前置条件。

交付范围为应用代码、Dockerfile、Docker Compose、相应验证和运行说明。用户自行完成实际 NAS 部署、域名及 HTTPS 配置；不以取得 NAS 访问权限、具体域名或完成正式部署作为本次开发前置条件。

## 一 已确定的产品规则

| 项目 | 当前决定 |
| - | - |
| 配对方式 | 1 至 4 位数字口令，A 设备上的口令输入 B 设备即可配对 |
| 相同口令 | 定位同一文件列表；第三台及后续设备须经任意一台已加入设备确认 |
| 不同口令 | 对应不同文件列表，服务端按配对关系约束访问 |
| 记住设备 | 配对后保存浏览器凭证，重新打开无需反复输入口令 |
| 固定口令 | 当前配对使用固定口令，不在每次传文件时重新生成 |
| 忘记口令 | 需要互传的设备重新输入同一个新口令即可，不做账号找回 |
| 用户界面 | 一个页面同时发送和接收，不要求选择或管理空间 |
| 文件用途 | 发布完成起最多保留 24 小时；首次服务端完整发送后保留 10 分钟供重试，后续成功不重新计时 |
| 文件容量 | 单文件上限 1 GB，全站 500 GB；不足时拒绝新上传，不清除未到期文件腾空间 |
| 展示名称与风格 | FileRelay／文件接力；尽量沿用现有 FileCodeBox 的视觉风格 |
| 管理后台 | 保留系统设置、容量和全站文件维护，不增加配对组管理产品功能 |

口令按字符串处理，保留前导零；例如 `007` 与 `7` 为不同口令。输入限制和展示形式在原型阶段统一，不能一端补零、另一端去零。

“设备”在首版指保存凭证的浏览器配置。同一物理设备上的不同浏览器、无痕窗口或清除网站数据后的浏览器，需要重新配对，不使用设备指纹识别。

相同口令定位同一组，不按真实用户区分。短口令不作为唯一个人身份；第三台及后续设备知道口令后仍需已有设备确认。待确认请求只能查看自己的申请状态，不能访问文件列表、元数据、上传或下载接口。

## 四 配对与日常使用流程

### 4.1 首次配对

A 打开首页，输入一个 1 至 4 位数字口令。服务端自动取得对应配对关系：未使用则建立；已使用则按该关系中已加入设备的数量执行直接配对或申请确认。A 页面显示当前配对口令，便于在 B 上照着输入。

B 打开同一个站点，输入相同口令，完成前两台设备的直接配对。第三台及后续设备输入口令后进入等待页，任意一台已加入设备同意后才获得文件访问凭证。人数判断以服务端保存的有效加入关系为依据，不能按当前在线数量判断；具体设备记忆和失效规则按第五章执行。

同一组不设置固定设备数量上限，第三台及后续均按相同确认流程加入。

加入请求有待确认、同意、拒绝和超时状态，自申请创建起 10 分钟未处理则过期，可以重新申请，不自动放行。确认只能由该组已加入设备执行，批准与凭证签发通过原子状态更新协调，重复或并发确认不重复加入。任意一台已有设备确认后不要求其他设备再次确认；等待期间不能提前返回文件内容。

配对成功后，服务端签发浏览器凭证。以后打开网站自动恢复该列表，口令保持固定，不需要每次输入，也不为每个文件生成另一套提取码。

### 4.2 日常传递

A 选择文件，页面逐项显示上传进度。服务端完成写入、校验和记录发布后，B 的列表自动出现该文件，点击即可下载。上传失败项可单独重试，已成功项不重传。

首页顶部保留当前配对口令、刷新状态及新设备加入请求提示，主体为上传入口、队列和统一文件列表，显示名称、大小、上传时间、过期时间、下载和删除。加入确认不扩展为成员角色或空间管理菜单。

视觉上尽量沿用现有 FileCodeBox 的主题、组件和交互样式，在此基础上调整配对页与共享列表，不以全新视觉重设计作为首版任务。

### 4.3 忘记与重新配对

记住状态有效时直接使用；忘记口令也不妨碍已有浏览器继续使用。需要重新配对时，通过一个“重新输入口令”入口重新提交，不提供空间列表或历史配对切换菜单。

重新输入不同口令更新当前浏览器的配对凭证，并按下文迁移其上传的文件。需要继续互传的其他设备也输入相同的新口令。原配对中的其他设备不被整体注销，不产生管理员重置流程。

已确认：重新配对成功后，当前浏览器之前上传且仍有效、未进入删除流程的文件跟随到新口令对应的列表。仅变更归属，不重传实体、不重置发布时间、24 小时总期限或已经开始的 10 分钟倒计时，不迁移其他设备上传的文件。

迁移必须在目标组加入权限成立后与当前设备归属更新协调提交；仍在等待批准、被拒绝或申请超时时，文件留在原关系。迁移后旧组不能再发起这些文件的新访问；已开始传输按统一租约规则处理，传输结果仍归对应文件，不因迁移丢失计时。

自动迁移需要当前浏览器仍持有原凭证来证明上传设备身份。清除网站数据或换浏览器后不能识别原上传设备，不凭共享短口令认领他人的上传文件。重新输入旧口令或已经使用的新口令均遵守加入规则，不能绕过第三台及后续设备确认。

### 4.4 刷新与异常

列表可见时建议每 2 秒轮询，打开页面、恢复前台和本机操作完成后立即刷新，隐藏时暂停，失败后退避。同页避免请求重叠，重新配对后忽略旧请求结果，防止不同列表混在一起。

刷新不重置上传队列或控件。请求失败显示重试状态，不显示为空列表。凭证失效后进入口令输入页；重新配对时停止旧关系的后续上传请求，旧上传不会自动转入新列表。

## 五 配对认证与内部数据

前台去掉空间概念，后端仍需要最小的配对关系来区分文件归属。同口令自动定位同一关系，是否获得访问权限按设备加入规则处理，不提供名称、slug、启用状态、角色或管理界面。

浏览器使用高强度随机凭证的 HttpOnly Cookie，数据库只保存凭证哈希。后续文件请求由服务端解析当前配对关系，不信任客户端传入的归属标识。短口令只在配对时提交，不放在下载 URL、逐次请求参数或日志中。

已配对页面通过自己的认证上下文取得当前口令用于显示，不向未配对访问者列出已使用口令或配对关系。配对接口对合法新口令自动建立关系，不要求管理员批准；第三台及后续的确认由已有普通设备执行。

同一浏览器配置只记住一组，重新配对替换该浏览器的旧凭证；同配置的标签页共享状态，后续检查到变化时清除旧列表并同步。已确认长期记住配对，不设置 30 天或 90 天的应用强制到期。浏览器 Cookie 本身仍受浏览器保存策略影响，清除网站数据、换浏览器或重新配对后按新状态处理，不能承诺跨清理识别物理设备。

凭证丢失后视为新设备，遵守现有加入数量与确认规则，不能凭共享口令恢复一个无法证明归属的旧凭证。没有可用旧设备确认时，可以使用另一个未占用口令重新配对，不自动放行原组申请。无法证明原上传设备身份的文件不自动迁移，留在原关系按原期限清理。

配对和重新配对接口执行限流、来源与 CSRF 校验，文件修改操作执行 CSRF 防护。生产 HTTPS 使用 Secure 和明确的 SameSite 属性，开发使用同源代理。配对限流不影响正常列表刷新。

| 对象 | 最小需要的内容 | 用途 |
| - | - | - |
| RelayGroup | 内部 id、规范化数字口令、创建时间 | 同口令取得同一文件归属，无用户管理功能 |
| Device | 服务端生成的内部 id、当前配对归属 | 识别持有凭证的浏览器，跟踪其上传文件，不使用硬件指纹 |
| DeviceSession | 凭证哈希、device_id、有效状态、必要的 CSRF 信息 | 长期记住浏览器，不设置应用强制定期到期；重新配对时替换凭证 |
| PairingRequest | 申请凭证哈希、目标关系、状态、有效期、确认设备及处理时间 | 隔离待确认设备，记录批准、拒绝及超时 |
| FileCodes | relay_group_id、uploader_device_id、发布完成时间、有效截止时间、领取与删除状态 | 文件归属、上传设备身份及临时生命周期 |
| UploadSession | 配对归属、文件身份、存储路径、状态、有效期、完成后的 file_id | 可靠续传、幂等发布和故障恢复 |
| UploadChunk | 所属上传会话、索引、实际长度、哈希和完成状态 | 分片校验与唯一约束 |
| StorageReservation | 配对与上传会话关联、大小及有效期 | 继续按全站计算容量 |
| DownloadAttempt | 文件与配对关联、状态、租约与保护上限、完成时间 | 下载保护和清理协调 |

不再新增原计划中的 Space、SpaceSession 或空间管理 API。具体字段和约束在工程阶段细化，优先复用现有模型与服务，避免为未来长期保存提前建立复杂策略系统。

普通接口建议使用 `/api/relay`，配对、申请状态、同意与拒绝、会话读取、重新配对、列表、上传、分片、下载和删除在第一阶段冻结契约。待确认凭证不能代替已加入设备凭证。前台使用统一站点首页，不新增 `/s/{slug}`。沿用现有 Hash 路由与管理员入口，API 和下载错误不被 SPA 兜底转换成成功页面。

不同配对关系的文件、分片、上传会话均按当前凭证约束，跨关系访问返回资源不存在。管理员 Token 不能自动代替设备凭证；设备认证失效与管理员 401 分别处理，互不清除对方状态。

## 六 上传可靠性与工程接通

### 6.1 上传与发布

配对认证的普通上传和分片上传共用容量预留、存储写入、文件校验、发布与失败清理服务。新前端改用普通上传接口后，再关闭旧 `/presign` 代理流程，不能仅关闭接口导致现有普通上传中断。

多文件逐项上传，不先在浏览器打 ZIP。队列每项具备进度、取消、失败原因与重试。服务端发布成功才算上传完成，不能以浏览器发送进度 100% 代替。

续传使用完整内容 SHA256、大小、名称和配对关系匹配，不能按首尾采样或元数据指纹自动复用。哈希采用分块增量计算，无法取得可靠身份时不退回弱指纹自动续传。重新选择文件恢复已有会话时也校验身份。

单文件上限已确认为 1 GB。校验文件和分片大小范围、非末片及末片准确长度、分片连续性、各片哈希、合并后实际总大小与完整 SHA256。零字节文件走明确的普通上传路径，禁止分片大小为零或负数。

上传会话保留上传中、合并中、已完成、取消和过期等状态，保存最终 file_id。重复或并发完成在有限期内返回同一结果，不重复发布、不破坏已发布文件。

全站文件容量上限已确认为 500 GB，所有配对组共用，不设置每组独立配额。额度或实际磁盘空间不足时拒绝新上传，保留未到期文件，不自动删除最旧文件腾空间。写入前保留会话与路径，写入和校验后提交文件记录及会话终态。崩溃、取消或发布失败可以恢复或清理，清理失败保留追踪记录。上传中和待物理删除的数据不能被错误当作已释放容量。

### 6.2 本地开发与镜像

直接使用 `frontend/` 现有源码及分层，复用上传进度、文件选择、粘贴和提示能力。调整 Vite 产物至后端实际读取的 `themes/2024`，开发增加同源 API 代理，生产由 FastAPI 提供同源页面和接口。

Dockerfile 构建本仓库前端，不再拉取上游主题；Compose 使用自建镜像或本地 build，保留数据卷。依赖安装和构建失败必须终止，避免命令链吞掉失败。

运行目标是 NAS 的 Docker／Container Manager、公网 HTTPS，手机可外网使用。使用本地存储、SQLite、单 worker，不增加 Redis 或 WebSocket。交付可构建的 Dockerfile、Compose 持久化配置与环境变量说明，验证镜像包含本地前后端修改；实际 NAS 架构、挂载路径、域名、HTTPS 与可信代理设置由用户部署时处理，不硬编码用户域名或 NAS 路径。

测试前配置可注入的数据根目录，将数据库、正式文件和测试文件分开。前后端现有检查、测试和生产构建纳入本仓库 CI。

## 七 临时文件与清理

### 7.1 已确认的保留规则

| 项目 | 当前处理 |
| - | - |
| 未领取保留时长 | 已确认：上传发布完成起最多 24 小时 |
| 下载后重试窗口 | 已确认：首次服务端完整发送后保留 10 分钟，后续成功不重新计时 |
| 长期保存 | 移出首版，不提供永久保存按钮及临时、长期切换 |
| 手动删除 | 同口令设备可删除当前列表文件，已开始下载按租约保护 |
| 清理扫描 | 建议每 60 秒；请求时即时判断有效期，不等待扫描 |

文件有效期与设备记忆分开：文件到期不会要求设备重新配对，设备记住得更久也不会延长文件寿命。保留时间由服务端统一配置，不增加每组配置或配额。

首版不实现长期文件或两天保留选项。将来调整规则时另行设计，不影响本版按 24 小时总期限和 10 分钟重试窗口实现。

### 7.2 下载后清理

已确认采用自动重试窗口：发布后待取件，任意设备（包括上传设备）首次服务端完整发送后，全组共享 10 分钟重试窗口，再次成功不延长。不等待每台接收设备都下载完成。失败不扣重试次数，也不因本次失败启动倒计时；无论失败次数多少，发布满 24 小时仍然过期。

截止时间采用以下规则：

`有效截止时间 = min(发布完成时间 + 24 小时, 首次完整发送时间 + 10 分钟)`

列表、元数据、HEAD、可识别的预取及未证明整体完成的 Range 请求不触发领取；中断和读取失败不认定完成。首版不提供自动请求内容的预览，单个 206 不等于完整下载，Range 整体合并判断属于 P1。

原生下载使用设备 Cookie，不将大文件整体读入前端内存；响应为 attachment。服务端正常发送完整响应不等于浏览器已经落盘，界面准确展示“传输完成，将在指定时间清理”。

不另加“确认取走”步骤；需要提前清理时使用已确定的手动删除操作。

### 7.3 删除与故障恢复

下载开始登记租约。已确认到期或手动删除时允许已开始的本次下载完成，拒绝新的下载，再等待有效传输结束或失联租约超时后物理删除。续租、失效时间和最长保护时间必须有限，并通过慢速和中断场景验证；不能把正常续租的传输当作已断开处理。

自动过期、用户删除和管理员删除共用状态与租约规则。删除先使文件不再接受新访问，再处理实体；取得删除状态后执行存储操作，不在长数据库事务中等待传输。

存储删除成功或确认目标不存在后才移除记录。失败保留待清理状态并重试，重启可恢复；旧过期任务接入或替换，不能独立绕过新状态。上传临时数据和分片同样保持失败可追踪，不误删正式文件。

NAS 本地引用始终只撤销分享记录，不能由到期或普通文件删除操作删除挂载原文件。

## 九 全新安装、持久化与恢复

已确认没有需要迁移的旧 FileCodeBox 数据，首版按全新安装开发，不承担旧数据库导入、历史永久文件转换或旧部署升级兼容。

全新数据卷可完成数据库初始化、系统初始化和配对。沿用迁移登记机制，新建结构及重复启动可正常执行；后续 FileRelay 自身结构升级仍需迁移记录，不把无旧数据理解为每次启动重建数据库。

数据库、文件和设备记忆持久化到 Compose 声明的数据卷，容器重建不丢失。短期到期规则及下载倒计时跨进程重启保留。文档说明备份需要同时覆盖数据库和文件，恢复时使用匹配版本；本次不实际操作用户 NAS 数据。

开发和测试使用可注入的独立根目录，只清理测试自己创建的数据，不递归删除仓库或正式目录。空库初始化、重复启动、容器重建及备份恢复流程形成验证或用户可执行说明；不将旧 FileCodeBox 历史库迁移列为首版验收。

## 十一 验收标准

| 场景 | 通过标准 |
| - | - |
| 两设备配对 | A 输入 1 至 4 位数字口令，B 输入相同口令，无创建空间步骤即可共用列表 |
| 第三设备与重复码 | 第三台及后续同码只创建申请；任意一台已有设备确认后加入；10 分钟未处理即过期；批准前无文件权限；并发确认不重复加入 |
| 设备记忆 | 刷新、重开以及容器重建后保留配对，不按固定天数强制失效；清除网站数据后视为新设备 |
| 忘记与重新配对 | A、B 可输入同一个新口令重新互传，无密码找回、管理员重置或空间切换列表 |
| 旧文件归属 | 目标加入成功后仅迁移当前设备上传的有效文件，原时间和倒计时不变；待确认不迁移，不认领其他设备文件 |
| 前导零与非法输入 | 各端口令规范一致，非法字符和超长输入被拒绝；不因整数转换误合并口令 |
| 同源认证与后台 | 配对及修改检查来源和 CSRF；设备失效不清除管理员 Token；管理员 Token 不替代设备身份 |
| 自动出现 | 网络正常、前台可见且列表请求 1 秒内完成时，上传发布后 3 秒内显示；打开和恢复立即刷新 |

| 文件完整性 | 普通、分片及零字节文件大小和完整 SHA256 正确；中间内容不同的采样相同文件不错误续传 |
| 分片与并发 | 非法长度、缺片和哈希错误拒绝发布；重复或并发完成仅生成一条文件，不破坏已发布结果 |
| 异码访问 | 不同配对关系不能互相列出、下载、修改、删除文件或操作上传会话；跨关系返回不存在 |
| 重新配对并发 | 标签页和迟到响应不混合两组列表；旧上传不自动发布到新口令下 |
| 下载与到期 | 任意设备含上传设备首次完整发送后，全组共享 10 分钟重试期；总期限 24 小时，不反复延长；元数据、HEAD 和未完成 Range 不领取 |
| 删除与断连 | 所有已加入设备可删除；到期或删除允许已开始传输完成、拒绝新下载；真实断连不误判完成，失联租约最终释放 |
| 文件与总容量 | 单文件 1 GB、全站 500 GB 上限准确执行；容量或磁盘不足拒绝新上传，不删除未到期文件 |
| 清理恢复 | 删除失败保留记录并重试，重启保留清理计划；文件有效期不随设备记忆自动延长 |
| 旧入口与 NAS | 旧提取码、分享、分片、预签名和 MCP 不能旁路访问；撤销引用不删除 NAS 原文件 |
| 初始化与持久化 | 全新数据卷初始化、重复启动和容器重建通过；设备、文件及倒计时持久化；无需旧 FileCodeBox 数据迁移 |
| 构建与范围 | 本地前后端进入镜像，Dockerfile 与 Compose 可交付，适用检查通过；不执行用户 NAS 部署、域名和 HTTPS 配置 |
| 品牌与页面 | 展示 FileRelay／文件接力，尽量沿用 FileCodeBox 风格；无空间管理、空间切换和永久保存流程 |
